# IncentiveTrap Contracts v1 — Slice A and B (proposed, not yet frozen)

Shapes are defined in `backend/app/core/schemas.py` and exported to `contracts/openapi.json` and `contracts/schemas/*.json`. This file records semantics only. Never hand-edit generated files. Slice A is frozen at the commit that merges it after review by P1, P3 and P4; after that, changes are additive only. Slice B (below) is also proposed and is finalized against P3's fixtures by G2.

## Conventions

- IDs are stable strings (`policy_id`, `customer_id`, `deal_id`, `ticket_id`, `incident_id`, `run_id`); never join on display names. `run_id` is the investigation ID.
- Timestamps are timezone-aware and serialized in UTC (`...Z`). Every analysis and recall uses an `as_of` cutoff and event time; future events must not leak.
- Money is `{amount_minor, currency}` (integer minor units, ISO code). Rates, discounts and interval bounds are fractions 0–1; a gap is a signed fraction (0.15 = 15 percentage points). Missing values are `null`, never 0.
- Unknown request fields are rejected (`extra="forbid"`).

## Metrics and statuses

`MetricName`: `discount`, `complaint_30d`, `cancel_30d` (also the token prefixes, e.g. `{{m:cancel_30d.gap}}`). Token fields: `month_end_value`, `other_value`, `gap`, `gap_lower`, `gap_upper`, `month_end_n`, `other_n`, `pre_policy_gap`, `status`. Constant tokens: `{{t:gap_threshold}}`, `{{t:baseline_margin}}`, `{{t:min_group_size}}`, `{{t:month_end_days}}`.
`MetricStatus`: `flagged`, `watch`, `no_signal`, `insufficient_data` (rules in `implementation_plan.md`). `AnalysisResult.flagged` is true only if at least one metric is `flagged` and at least two distinct customers corroborate it.

## Explanation rules the contract relies on

- Text fields in `Explanation` are resolved for display; `template_text` keeps tokenized originals for audit.
- `explanation_source` is `reflect` or `template` (deterministic fallback, with `validation_error_codes`).
- `memory_status` is `live`, `unavailable` or `fixture`; a stub or recording is never `live`.
- `Recommendation.action_type` is one of `adjust_policy`, `pilot_guardrail`, `revert_change`, `collect_more_data`, `no_action`. `success_metric` and `guardrail` are proposed targets, not calculated values. `history_influence` lists `RecalledMemory.id`s; empty when memory is off. No numeric confidence score exists.
- `Evidence.excerpt` is display-only untrusted customer text and is never sent to a model.

## Errors

Every error body is `{code, message, request_id, details[]}`. Codes: `validation_error` (422), `not_found` (404), `forbidden` (403), `scenario_not_loaded` (409), `as_of_before_memory` (409), `retention_pending` (409), `idempotency_conflict` (409), `not_implemented` (501), `internal_error` (500). The `x-request-id` response header repeats `request_id`.


## Module signatures

- P3: `analyze(dataset, policy_id, as_of) -> AnalysisResult`
- P4: `explain(analysis, context) -> Explanation`

## Slice B: dataset, incidents, outcomes

- **Dataset file** (`data/scenarios/<scenario>.json`, P3): `Dataset` with `meta` (`synthetic`, `generator_version`, `text_version`), `policies`, `customers`, `deals`, `tickets`, `cancellations`, `history`. The loader checks every cross-reference by stable ID (deal to policy/customer, ticket and cancellation to deal and matching customer) and rejects duplicate IDs. Scenario names match `[a-z0-9-]` and the file name must equal `meta.scenario`. The batch checksum is the SHA-256 of the file bytes.
- **Run state in SQLite only:** loaded batches, investigations, incidents, outcomes. Business records stay in the fixture files.
- **Investigations:** `run_id` is generated by the server. The same `idempotency_key` with the same body returns the stored run (200); with a different body, `409 idempotency_conflict`. `incident_id` is `inc-<policy_id>-<comparison_id>`, or `null` when the analysis has insufficient data. `analysis_digest` is SHA-256 of the canonical JSON of the `AnalysisResult`, so identical numbers give identical digests regardless of `memory_mode`.
- **Memory guards:** a `live` run with `as_of` before the latest *retained* outcome event returns `409 as_of_before_memory`; a `live` run on an incident with a `pending` outcome returns `409 retention_pending`. `memory_mode: off` is never blocked by either.
- **Outcomes:** `POST /api/incidents/{id}/outcomes` stores the outcome as `pending`, calls P4's `retain_outcome`, and records `retained` or `failed` with a non-secret reason; a failure keeps the outcome. `run_id` must belong to the incident. Notes are capped at 280 characters and stripped of control characters, angle brackets and backticks. `POST /api/outcomes/{id}/retention` retries; it is a no-op once `retained`.
- **Demo:** `POST /api/demo/load` is idempotent by checksum and seeds history through `seed_history` (a changed file reseeds). `POST /api/demo/reset` needs `DEMO_RESET_ENABLED=true` and `confirm: true`, clears that scenario's SQLite state and calls `reset_demo_bank`; P2 refuses banks without the `incento-demo-` prefix.
- **Module wiring:** `core/modules.py` uses `app.analysis.service.analyze` and the four `app.memory.service` functions (`explain`, `retain_outcome`, `seed_history`, `reset_demo_bank`) when they exist; otherwise it uses the labeled stubs in `core/stubs.py`. `GET /api/health` lists `stubbed_modules`. Stub analysis reports `insufficient_data`; stub explanations are `template` with memory status `unavailable`, never `live`.
- **Signatures P4 implements:** `explain(analysis: AnalysisResult, context: ExplainContext) -> Explanation`, `retain_outcome(outcome: Outcome) -> RetentionResult`, `seed_history(incidents: list[HistoricalIncident]) -> SeedResult`, `reset_demo_bank(scenario: str) -> ResetResult`.
